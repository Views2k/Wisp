# Offline lossless decoder comparison

This diagnostic reads only the specifically reported, hash-pinned MP4. It loads the retained installer's exact 24-file native decoder set and matching LibVLCSharp assembly. It creates no window, captures nothing, disables audio and hardware decoding, requires Wisp/Forza closed, and leaves the source held read-only through decoder cleanup. Outputs go only to a new checkout `work` directory. Root owns builds and execution.

**Current measurement correction:** earlier versions converted and hashed every 4K callback during playback. Logged default spent 1459 ms in 77 callbacks; short-prefetch spent 893 ms in 47 callbacks, both approximately 19 ms per callback, exceeding a 60 fps frame interval. Their FIFO resets are real observations, but later lateness/throughput are materially perturbed by the observer and cannot reject a cache policy for normal playback. The current version preallocates three image buffers, copies only callback ordinals 0/42/75, and converts/hashes those copies **after player, media and engine disposal**. Other callbacks record only ordinal/phase/time and have null `RgbSha256`. Decoder log counters and all playback controls remain unchanged. Root will compare fresh `default` and `short-prefetch` runs using this same lightweight observer.

Run each policy in a fresh process with identical source/payload arguments. `default` retains VLC's frame-dropping defaults. `no-hurry` changes **only** `--no-avcodec-hurry-up`. Both reproduce product `:start-paused`, wait for Paused, seek to zero for a preview frame, then explicitly resume.

Pinned VLC 3.0.24 source (`work/lossless-dependencies/vlc-3.0.24.tar.xz`) establishes the hypothesis:

- `modules/codec/avcodec/avcodec.c` defaults `avcodec-hurry-up=true` and `avcodec-skip-frame=0`.
- `modules/codec/avcodec/video.c`, `check_frame_should_be_dropped`, drops whole compressed blocks after more than 11 late frames. Its comment explicitly notes picture corruption until a new I-frame. The decoder calls this function only when hurry-up is enabled. The separate five-second lateness guard remains unchanged in both arms.
- Existing product playback leaves these defaults unchanged. This makes the comparison justified; it does not establish the reported cause without results.

Build with `WispDecoderPayload` set to the absolute retained payload directory. No package is restored by this project; the managed reference is copied from that payload. The build argument and runtime payload must match by hash.

Arguments: `--source <absolute reported MP4> --payload <absolute retained payload> --output <fresh absolute checkout work directory> --policy default|no-hurry|one-thread|no-direct-rendering|short-prefetch`.

The first actual comparison reproduced the corruption in both `default` and `no-hurry`: 39/73 and 44/80 callbacks, respectively, did not match any independent FFmpeg RGB frame. Both first mismatches were `25F4288632BF2122FEE3421763D8F85A9BCE8A00665A28126B1DA92966ABA2C5`, immediately after callbacks matching media frames 5/6. Hurry-up is therefore not an evidenced fix. Reports remain under `work/clips-short-save-20261001/decode-{default,no-hurry}-01`.

The isolated `one-thread` policy differs from **default only** by `--avcodec-threads=1`; hurry-up remains at its default. It also reproduced corruption: 15/28 callbacks were unmatched, with the first mismatch `97745081ED0036D02AE00F371ADD90D9184F1F555DF184890C4445568DB3CCA6` at 2.196 seconds. Pinned `video.c` maps the default thread count of zero to CPU count plus one (when >1), capped at six for H264, and does not disable H264 frame threading for this codec version. The packaged codec contains `Lavc62.28.102`/`Lavf62.12.102`, consistent with the source companion's FFmpeg 8.1.2. No thread-count product correction is supported by these results.

The next isolated `no-direct-rendering` policy changes **only** `--no-avcodec-dr` relative to default. Pinned `avcodec.c` enables this option by default. `video.c:lavc_GetFrame` selects VLC-owned picture-pool buffers via `lavc_dr_GetFrame` when enabled; disabling it selects `avcodec_default_get_buffer2`, then `lavc_CopyPicture` copies each decoded plane to VLC's picture. This isolates reference-buffer ownership/allocation while preserving the decoder, thread count, seeking, frame-dropping defaults and RGB output. Source inspection did not establish an ownership defect, so this remains a diagnostic boundary, not an accepted fix.

The other global frame-drop controls do not directly explain the first damaged reference image: `skip-frames` is consumed by `codec/synchro.c`, which `modules/codec/Makefile.am` links into `libmpeg2`, not the avcodec H264 decoder. `drop-late-frames` discards already-decoded pictures in `src/video_output/video_output.c`. The independent `video.c:check_block_being_late` compressed-block guard requires more than five seconds after its observed lateness start, whereas the no-hurry arm's first corrupted callback occurred about 2.22 seconds after process startup. These findings do not exclude later timing-related drops or prove realtime playback quality.

The no-direct-rendering arm also reproduced corruption: 44/79 callbacks were unmatched, with the same first bad RGB hash as default/no-hurry. No player setting change is supported. Hashes recover after the next IDR around media frame 120.

The next check instruments the original clip with the **default policy**. Pinned `src/input/decoder.c:input_DecoderDecode` clears compressed blocks when its FIFO exceeds 400 MiB and output pacing is off, independently of all the options above. The clip's approximately 3.12 Gbit/s makes this a concrete boundary to observe, not an established cause. `DecoderLogCounters` attaches a native callback to the exact held decoder DLL. It compares only fixed format strings for FIFO resets, hurry drops and the five-second guard, without reading format arguments, retaining text or writing logs. The report contains counts and first observed elapsed times only. `ObservedMessages` confirms the callback actually received logs. Direct callback use avoids LibVLCSharp's per-message Task.Run dispatch and its timing ambiguity. The callback is detached through libvlc_log_unset's barrier before freeing its delegate/module; no playback options change.

The logged default run **confirmed one compressed FIFO reset at 1215.29 ms**, with 590 observed log messages and zero hurry/five-second drops. Report: `work/clips-short-save-20261001/decode-logged-default-01/decode.json`. This establishes that reference-bearing compressed packets were discarded in this run. Pinned `src/libvlc-module.c` defaults `file-caching` to 1000 ms; local `modules/access/file.c` returns it as the PTS delay, and `src/input/es_out.c` uses that delay to decide when initial buffering completes. Normal playback's `b_out_pace_control` remains false.

The next `short-prefetch` policy changes **only** the media option `:file-caching=100`. It retains paused opening, the same seek to zero and explicit resume, the same decoder settings and the same output timing. This tests whether a smaller initial encoded queue avoids the measured reset while keeping a real preparation phase. MP4 demux advances in 250 ms increments, so 100 ms is not a byte cap or a guarantee for arbitrarily large lossless packets. Acceptance requires zero FIFO resets and zero unmatched RGB callbacks against the independent oracle; realtime performance and every decoded frame still require separate evidence.

That check failed: `decode-short-prefetch-01/decode.json` records one FIFO reset at 2629.72 ms and 14 hurry drops (first at 1881.54 ms), with 20/47 callbacks unmatched. The logged default comparison has 43/77 unmatched callbacks and its FIFO reset precedes the first corrupt callback. Reducing the cache did not establish a fix; do not apply any tested policy to product code from this evidence.

The pinned normal-player API exposes no encoded-FIFO backpressure setting. `input.c` initializes `b_out_pace_control=false`; `es_out.c` changes it for stream-output pipelines. Media read/seek callbacks do not receive decoder queue occupancy. `stream_out/display.c` still sends compressed blocks with `input_DecoderDecode(..., false)`, so a display-only stream-output chain does not remove the unsafe queue. Offline transcoding differs: `stream_out/transcode/transcode.c` sets its decoder's `b_frame_drop_allowed=false`, and `transcode/video.c` calls decoding synchronously. A fully prepared playback-only proxy is a possible separate design, but the current 24-file runtime lacks the required stream-output/encoder/mux plugins. No proxy implementation or additional dependency is authorized by this diagnostic report itself.

No file deletion or source copy.

`decode.json` records every callback's ordinal, phase and time; only the three sampled callbacks have exact RGB SHA256 values. Their BMPs use callback ordinals 0/42/75. **Callback ordinals are not media-frame indices**: paused seeking, preroll and frame dropping can repeat or omit frames. Align non-null hashes against independent FFmpeg RGB24 per-frame hashes before comparing images. The diagnostic converts RV32 BGR-padding to RGB24 without scaling or a color adjustment, after native teardown. Native callbacks do not convert/hash pixels, call LibVLC, write files or use UI. Cumulative callback elapsed wall time and post-decoder pixel processing time are reported separately. Three matching samples do not establish that every frame was correct, and this remains a software/vmem observer rather than actual D3D player performance or A/V-sync proof.

The source remains held against write/delete; decoder DLLs and parent directories stay pinned. A cleanup hang ends the diagnostic process at its unchanged hard deadline. No product correction is included.
