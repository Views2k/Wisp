# Shader maintenance

WPF embeds the checked-in `.ps` files under `src/Wisp.App/Shaders`. Editing HLSL
alone does not update those WPF shaders; regenerate their bytecode as described
below. The live combustion Analogue HUD uses a separate Direct3D11 build of the
same material sources.

| Source | Packaged bytecode | Define | Compiler flags |
| --- | --- | --- | --- |
| `AnalogGauge.hlsl` | `AnalogGauge.ps` | None | `0x8000` (optimization level 3) |
| `DigitalGauge.hlsl` | `DigitalGauge.ps` | None | `0x8000` (optimization level 3) |
| `AnalogNeedle.hlsl` | `AnalogNeedle.ps` | None | `0` (default) |
| `AnalogNeedle.hlsl` | `ElectricAnalogNeedle.ps` | `ELECTRIC_NEEDLE=1` | `0` (default) |

Each source exposes the `main` entry point. These are WPF pixel shaders; the
Native HUD uses Shader Model 3.0 bytecode. Both needle variants must be regenerated
when their shared HLSL changes.

## Direct3D11 renderer

The application build invokes `src/Wisp.NativeRenderer/Build-NativeRenderer.ps1`
when its native sources or shared Analogue HLSL change. This requires Visual
Studio C++ build tools for x64 and the Windows SDK's `fxc.exe`.

The script adapts the shader bindings and entry points of `AnalogGauge.hlsl` and
`AnalogNeedle.hlsl` to Shader Model 5.0, preserving their material calculations.
It compiles those shaders and the image/quad shaders in `Quad.hlsl`, then embeds
the generated bytecode in `Wisp.NativeRenderer.dll`. The DLL is copied alongside
the application during build and publish. Digital, electric and WPF preview
shaders continue using the checked-in PS 3.0 files above.

To build the native renderer and run its contract checks directly:

```[WINDOWS POWERSHELL]
.\src\Wisp.NativeRenderer\Build-NativeRenderer.ps1 -RunContractTests
```

Changes to shared material HLSL need both the native build and WPF bytecode
regeneration. Review GPU output for each path; a software WPF capture cannot
validate either live renderer's presentation timing.

## Regenerate for review

On Windows, run the helper from the repository checkout:

```[WINDOWS POWERSHELL]
.\tools\Build-Shaders.ps1 -OutputDirectory .\work\shader-review
```

The helper calls `D3DCompile` from Windows' System32 `D3DCompiler_47.dll`, using
entry point `main`, target `ps_3_0`, and the flags and define above. No separate
`fxc.exe` or .NET application build is required. It prints the compiler version
and each output's SHA-256, requires a new or empty output directory, and refuses
to write into the packaged shader directory.

With `D3DCompiler_47.dll` file version `10.0.26100.9168`, this command reproduced
all four bytecode files in the published Wisp 1.0.12 source byte-for-byte.
Other compiler versions may produce different bytes. Record the reported
compiler version when reviewing a change, and compare the generated bytecode
with its matching source before replacing packaged files.

Shader bytecode is a deliberate exception to the generated-output rule. Keep
the existing shader contract checks and validate the result in the GPU-rendered
HUD; software UI-review captures cannot establish shader output parity.
